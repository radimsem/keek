# Cua #6210 turn clock fix: implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Each turn's `t_ms_from_session_start` matches the turn's position in `recording.mp4`, and ffmpeg's `duration_ms` covers the whole video, delivered as a draft PR to `trycua/cua` that refs [#6210](https://github.com/trycua/cua/issues/6210).

**Tech stack:** Rust 1.97.1 (pinned by `libs/cua-driver/rust/rust-toolchain.toml`), cargo, wf-recorder, nested Hyprland 0.56.2, ffmpeg.

**Spec:** the issue body of #6210. Source read at `trycua/cua` main `a9902d2`; `recording.rs`, `video_wayland.rs` and `video_ffmpeg.rs` are unchanged since the issue's `895ede5`, so its line numbers hold.

## Is the 1.5 s offset intentional?

Checked on 2026-10-31 in the code, git history, docs and the PRs that touched these lines. The startup probe is deliberate. The offset it causes is not, as far as every source shows. No maintainer has confirmed this, because #6210 has no reply yet.

**The probe has a stated purpose, and it isn't timing.** The comment at `video_ffmpeg.rs:105-107` says it surfaces stderr when ffmpeg dies on startup, so a session doesn't record a useless empty mp4. #1720 describes it as a fast-fail for an ffmpeg subprocess that hung on a macOS TCC prompt. This plan keeps it.

**The history shows a regression:**

| Date | PR | What happened |
| --- | --- | --- |
| 2026-05-26 | #1718 | Adds the anchor with the comment that video, cursor and turn times "line up at the millisecond". `VideoRecorder::start` returned right after the spawn, so reading `now_ms()` after it cost almost nothing. |
| 2026-05-26 | #1720 | Adds the 1.5 s probe inside the backend's `start`. `recording.rs` has no clock line in that diff, so the turn clock moved 1.5 s without anyone touching it. |
| 2026-07-12 | #2182 | Copies the probe into wf-recorder. Its `started_at` goes before the spawn. |
| 2026-10-14 | #4994, #5145 | Fixes the overwritten `session.json` value. #4994 says `session_start_ms` "remains at its existing capture point", which scopes it out and gives no reason for the position. |

**Nothing depends on the offset:**

- The code's own comment at `recording.rs:646-649` promises the opposite.
- `recording_render` applies `t_ms` straight onto the video's timeline, with no 1.5 s correction: the click's `t_ms` becomes the zoom region's start.
- `cursor.jsonl` already counts from the anchor, so today it disagrees with the turn log on the same recording.
- No test pins the delay. The two 1500 ms constants under `cua-driver-e2e/tests` are macOS window settling.
- `RECORDING.md` and the `start_recording` reference page don't describe the relative fields or mention a lead-in.
- The video does contain frames from during the probe: that's why the spike saw a click 1.45 s late rather than on time.

## Design decision

Use the narrow fix from the issue: move `let started_at_ms = now_ms();` from `recording.rs:690` to directly after `let monotonic_start = Instant::now();` at line 650.

Considered and rejected for this PR:

- **Compute offsets from `session_monotonic_start`:** removes the wall clock, but `recording_action_timestamp.rs` pins `timestamp` and the relative fields to one anchor, and `start_ms` arrives from the dispatcher as wall-clock ms. It touches more call sites for a clock-step risk nobody has reported.
- **Have each backend report its first-frame instant:** the accurate answer, but it changes the `VideoBackend` trait on three platforms.

**Known residual, to state in the PR:** the zero moves to just before the backend starts, so a backend's real startup latency now shows as a small positive offset.

- wf-recorder: about 50 ms measured.
- ffmpeg: not measured, but no longer 1.5 s the wrong way.
- ScreenCaptureKit (`video_sckit.rs:156-241`): has no probe, so its old clock read close to `start_capture` returning. It now gains the time spent in `SCShareableContent::get` and stream setup. This is the one backend that could get slightly worse, and it can't be measured from this machine. `cursor.jsonl` already uses this anchor on macOS, so the turn log comes into line with it.

**ffmpeg's `duration_ms`, fixed here too:** the bug is present, with the same origin. `video_ffmpeg.rs:132` sets `started_at` after the probe, and `stop` reports `started_at.elapsed()` at line 140. The video keeps every frame from the probe, so `duration_ms` reads about 1.5 s short on Windows and X11. It contradicts its own doc at `video.rs:30` ("duration the recorder was active"), and the wf-recorder backend sets it before the spawn (`video_wayland.rs:197`).

It belongs in this PR because the clock fix would otherwise create a new inconsistency: on ffmpeg, a late turn could read up to 1.5 s past the `duration_ms` in the same recording. Today's impact is small. The field's only in-repo reader is `session.json`, because `recording_render` asks ffprobe for the duration, but external tools read that file.

The fix moves one line: `let started_at = Instant::now();` directly before `cmd.spawn()`. ScreenCaptureKit and the GNOME backend set `started_at` after a short startup with no probe, so they stay as they are.

## Review focus

Input classes no task's test exercises, most likely first:

1. **macOS video:** the turn log may lead the video by the setup time above. Requires maintainer macOS evidence; listed as a gap.
2. **Windows and X11 ffmpeg:** expected to improve by about 1.5 s minus ffmpeg's startup. Not run locally; listed as a gap.
3. **Video fails to start:** `record_video: true` with a backend that errors after its probe. The turn log now counts from before the attempt, which matches `cursor.jsonl`. No video exists to misalign, so no test is added.
4. **First turn in a session:** `start` holds the session lock during the probe, so a first turn now reads about 1500 ms instead of about 0. `recording_loader.rs` only reads these as positions, so this is correct. Task 2 runs the crate's tests to confirm nothing assumes otherwise.
5. **Wall-clock step during a recording:** an existing risk that this change leaves as it is.

- [ ] **Step 1: Write the failing test**

Move the three fixture setters at the top of the existing test into `fn install_capture_fixtures()`, and call it from both tests. Then add a fake backend and this test. The factory sleeps `STARTUP_MS` before returning, as the real probes do. It records `now_ms()` on entry in a static `AtomicU64`. Its backend's `stop` writes a non-empty file at the output path, because `validate_video_metadata` rejects a missing or empty file, and returns `finalized: true`.

```rust
const STARTUP_MS: u64 = 300;

#[test]
fn turn_times_count_from_before_the_video_backend_starts() {
    install_capture_fixtures();
    set_video_backend_factory(Box::new(SlowStartFactory));
    let directory = tempfile::tempdir().unwrap();
    let recording = RecordingSession::new();
    recording
        .start(directory.path().to_str().unwrap(), true, None)
        .unwrap();
    let pending = recording
        .begin_turn("press_key", &json!({"pid": 1, "key": "a"}), now_ms(), RecordingCaller::default())
        .unwrap();
    recording.finish_turn_with_outcome(pending, "Pressed a", None, false);
    recording.stop_owner(None).unwrap();

    let action = read_json(directory.path().join("turn-00001").join("action.json"));
    let session = read_json(directory.path().join("session.json"));
    // Margin below STARTUP_MS because these are wall-clock ms; the bug reads near 0.
    assert!(action["t_start_ms_from_session_start"].as_u64().unwrap() >= STARTUP_MS - 50);
    assert_eq!(session["video"]["present"], true);
    assert!(session["started_at_monotonic_ms"].as_u64().unwrap() <= FACTORY_ENTERED_MS.load(Ordering::SeqCst));
}
```

The factory's `OnceLock` is per test binary. The existing test passes `record_video: false`, so it never reaches the factory.
